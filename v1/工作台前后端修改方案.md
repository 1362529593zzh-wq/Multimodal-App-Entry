# 工作台前后端修改方案

## 1. 背景与目标

本方案基于当前工作台页面实现和最新预览图进行整理，目标是把现有“工作台基础壳子”升级为更接近常见大模型工作台的交互形态：

- 左栏进入工作台后直接展示会话管理区
- 中间区域展示可滚动的消息流
- 底部输入区固定，不随消息滚动而漂移
- 输入区内提供能力功能条：图像识别、图像生成/文生图、文生语音、文生 PPT、文生视频
- 点击能力后，在同一输入区位置展开该能力对应的参数配置，不跳转页面
- 参数项支持按能力切换，例如风格、比例、模板、页数、时长、音色等

本方案优先保证：

1. 前端 UI 结构先落地
2. 后端接口最小改造即可支撑第一版交互
3. 后续能力扩展时不需要再次推翻工作台结构

## 4. 目标 UI 结构拆解

结合预览图，工作台建议拆成 3 个稳定区块：

### 4.1 左侧会话栏

上半区：

- `新建对话` 按钮
- `搜索历史对话` 输入框

下半区：

- 历史会话列表
- 支持高亮当前会话
- 支持展示最近时间、最近预览、能力标签

### 4.2 中间消息区

- 首屏为空时展示欢迎语和推荐能力/推荐问题
- 已有消息时展示用户消息、助手消息、任务状态卡、结果卡
- 该区域单独滚动
- 保持底部自动滚动到最新消息

### 4.3 底部固定输入区

默认态：

- 文本输入
- 能力功能条
- 发送按钮

展开态：

- 当前能力标签
- 附件入口或参考图入口
- 模型、风格、比例、模板、时长、页数等能力相关参数
- 不同能力切换时只替换参数区，不替换整个工作台页面

## 6. 后端修改方案

## 6.1 会话搜索

现有接口：

- `GET /api/workbench/conversations?scope=active`

建议升级为：

- `GET /api/workbench/conversations?scope=active&keyword=海报`

改造点：

- `WorkbenchController` 增加 `keyword` 参数
- `WorkbenchService` 增加搜索参数
- `WorkbenchServiceImpl` 在 `chat_session.title`、最近消息摘要上支持模糊过滤

优先建议先做标题搜索，后续再补最近消息摘要搜索。

## 6.2 能力输入 schema 下发

当前前端参数蓝图主要在：

- `E:\shupai\Multimodal App Entry\frontend\src\pages\workbench\mock.ts`

建议把这部分迁移为后端驱动。

建议新增接口：

- `GET /api/workbench/functions/{functionCode}/composer-schema`

返回内容建议包含：

- 输入框 placeholder
- 能力标签
- 是否支持上传
- 字段列表
- 每个字段的类型、选项、默认值、展示顺序

建议优先复用现有配置体系：

- `function_config`
- `model_service`
- `param_template`

推荐做法：

1. `function_config` 维护能力基础信息
2. `model_service.supported_options` 补充模型级能力支持
3. `param_template` 增加 `templateType=composer_schema` 用于保存工作台输入 schema

这样可以避免新建太多表。

## 6.3 工作台附件上传

为了支撑“图像识别”和“图像生成参考图”，建议新增：

- `POST /api/workbench/assets/upload`

作用：

- 上传图片/音频/文档等输入素材
- 返回 `fileId`、预览地址、下载地址、mimeType`

后续 `POST /api/workbench/chat` 时将附件 ID 作为：

- `sourceAssetIds`

传入任务。

## 6.4 聊天提交结构增强

现有 `POST /api/workbench/chat` 已支持：

- `capability`
- `model`
- `options`
- `parentTaskId`
- `sourceAssetIds`

建议增强：

1. `options` 从“任意 JSON 字符串”升级为更明确的结构化对象
2. 增加 `schemaVersion`
3. 增加 `templateCode`
4. 增加 `attachments`

如果短期不想破坏现有接口，可保留兼容策略：

- 第一阶段仍允许 `options: string`
- 第二阶段新增 `composerOptions: object`

## 6.5 消息与结果结构增强

当前消息可分为：

- 文本消息
- 状态消息
- 结果消息

建议补充结果元数据：

- `resultKind`
- `previewAssets`
- `downloadAssets`
- `suggestedFollowUps`
- `structuredPayload`

这样前端结果卡才能更自然地区分：

- 图像生成结果
- 图像识别结果
- 语音文件结果
- PPT 文件结果
- 视频文件结果

## 6.6 消息加载策略

当前：

- 会话消息一次性全量拉取

建议分阶段：

### 第一阶段

- 继续全量拉取
- 保证 UI 先改完

### 第二阶段

- 增加分页或 cursor
- 接口示例：`GET /api/workbench/conversations/{conversationId}/messages?cursor=...&size=50`

如果后续会话量不大，第一阶段可以先不动。

## 6.7 任务更新机制

当前：

- 前端轮询 `GET /api/workbench/tasks/{taskId}`

建议：

- 第一阶段继续轮询
- 第二阶段再考虑 SSE / WebSocket

原因：

- 先改 UI，联调成本最低
- 现有后端任务链路已可工作

## 10. 验收标准

完成后建议至少满足以下标准：

1. 进入工作台默认看到左会话栏 + 中部欢迎区 + 底部固定输入区
2. 左栏可新建对话、搜索历史会话、切换会话
3. 消息区可独立滚动，输入区不移动
4. 点击不同能力后，输入区参数即时切换
5. 图像生成可展示风格、比例、模板、参考图等配置
6. 会话与消息读取不报错，现有任务轮询链路可继续工作
7. 至少图像生成能力能走通“输入 -> 提交 -> 状态 -> 结果回流”

---

## 11. 结论

这次工作台改造不建议推翻现有工作台页面，而建议在当前骨架上做“产品化重构”：

- 前端重点改布局、输入区和能力展开机制
- 后端重点补搜索、schema、附件上传
- 任务轮询和结果回流链路先复用现有实现

这样可以在改动量可控的前提下，较快把工作台做成接近目标预览图的形态，并且为后续多模态能力继续扩展留出接口空间。
